# v0.5 Local API Design Contract

**Status:** The owner merged schema/security corrections in [PR #414](https://github.com/geoffrey-xiao/deprail/pull/414). No independent approval is recorded, and none is required under [ADR-0005](../../adr/ADR-0005-solo-owner-review-policy.md). The OpenAPI and local security profile remain proposed pending the owner's technical decisions and evidence; runtime implementation is not yet approved.
**Design inputs:** [`PRD-v0.5.md`](PRD-v0.5.md), [`UX-DESIGN.md`](UX-DESIGN.md), [`ARCHITECTURE-v0.5.md`](ARCHITECTURE-v0.5.md).

## 1. Goal and constraints

Define the smallest same-origin local API needed by the candidate history and scan-detail UX. The API delegates to shared application services and returns versioned domain meaning. It does not reimplement scan logic, become a general extension platform, or imply team/cloud functionality. The proposed initial surface is read-only; browser-triggered scanning or mutation is excluded unless explicitly reconsidered through release change control.

The candidate OpenAPI 3.1 contract is [`schemas/openapi/v1/openapi.yaml`](../../../schemas/openapi/v1/openapi.yaml). It is a required design-stage artifact before API implementation, not an approved runtime contract.

## 2. Proposed resource model (unapproved)

- **HistoryEntrySummary:** unique `historyEntryID` per stored operation, recorded time, `sourceScanID` from the existing report, `operationOutcome` (`completed|failed|cancelled`), optional `reportStatus` (`complete|partial|failed`), root display label under privacy contract, counts, and minimal provenance summary.
- **HistoryEntryDetail:** summary plus allowlisted report metadata and required nullable typed provenance (`deprailVersion`, `scannerName`, `scannerVersion`, `scannerDatabaseVersion`) when a report exists, safe diagnostics, and artifact-integrity states. Unknown provenance is null, never inferred from findings/raw text. Never expose raw report/project JSON.
- **WorkspaceSummary:** stable workspace ID, repository-relative path and safe ecosystem/manager fields only when captured from the same operation's validated graph. Any exposed `discoveryCompleteness` is discovery-only, not per-workspace scan success; absent graph context is unavailable, not a confirmed empty workspace collection.
- **FindingSummary:** key derived through the existing stable-finding identity rule, package identity, aliases, available severity and fixed version, and validated repository-relative workspace context. Raw artifact digests are report-level references; do not attach one to a finding or invent a dependency path/evidence source without a verified source mapping.
- **ApiError:** stable API error code and concise safe message; no request ID, stack trace, secrets, raw paths, or echoed input.

Existing CLI/report semantics remain the source of scan meaning; the API must not invent vulnerability, completeness, or workspace-scan states. The OpenAPI candidate uses separately paged workspace/finding collections; response fields remain a strict projection of the candidate `history-v1` model, not a copy of its stored JSON.

**Owner-selected report boundary, not yet accepted:** [ADR-0004's direction](../../adr/ADR-0004-local-scan-history.md#owner-selected-direction-independent-history-projection-not-accepted) keeps existing `ScanReport`/CLI serialization unchanged and proposes a separate, allowlisted `history-v1` storage projection. `HistoryEntryDetail` and child collections translate only approved projected fields; they must not embed the stored JSON wholesale, raw `ScanReport`, raw errors, absolute host paths, or fabricated tool/evidence provenance. [`FAILURE-AND-DATA-CONTRACT.md`](requirements/FAILURE-AND-DATA-CONTRACT.md#candidate-history-v1-projection-object) defines candidate source-to-projection fields, including stable keys from `normalize.StableFindingKey`, nullable report/collections and safe diagnostics. The owner must accept that exact field, unknown-data, and redaction mapping before OpenAPI schemas/examples are frozen; external review is optional under ADR-0005. A missing or unsafe projection is a typed failure, not an empty successful detail.

## 4. Query and deterministic ordering

The versioned candidate is [`schemas/openapi/v1/openapi.yaml`](../../../schemas/openapi/v1/openapi.yaml). It defines `pageSize` (default 25, range 1–50) and an opaque, URL-safe keyset `cursor` (maximum 512 characters); there are no filters, offsets, arbitrary sort expressions, or client-provided SQL.

- History is ordered by `recordedAt DESC, historyEntryID DESC`.
- Workspaces are ordered by `workspaceID ASC`; findings are ordered by `stableFindingKey ASC`.
- A cursor is bound to API version, resource, parent history-entry ID where applicable, and the last ordering tuple. It is not an authorization token and contains no repository data.
- No cursor expiry is proposed because v0.5 has no history deletion or automatic eviction. A contract-version change invalidates cursors from the older API version.
- Keyset pagination avoids offset shifts. It does not promise a database snapshot across requests; clients restart pagination to include newly recorded entries.
- Unknown query parameters, malformed cursors, unsupported cursor versions, and page sizes outside the contract fail with `API_REQUEST_INVALID`.

Every successful response is limited to 1 MiB of fully serialized UTF-8 JSON bytes, including framing, required escaping and `nextCursor`. Requested page size is an item ceiling, not a guaranteed number of returned records. Build each collection page from whole records that fit both the requested count and byte budget; a short page retains a cursor from the last emitted ordering tuple whenever more records remain. Never skip an unreturned record or emit a zero-item nonterminal page. If the first record plus its envelope cannot fit, or an indivisible detail response exceeds the cap, return bounded `500 API_RESPONSE_TOO_LARGE` before sending any success body. JSON Schema `maxLength` counts code points rather than encoded bytes; measure the actual encoded response, including cursor overhead. These engineering selections follow [ADR-0004's addendum](../../adr/ADR-0004-local-scan-history.md#detailed-engineering-selections-for-owner-review); owner contract acceptance and runtime verification remain outstanding.

## 5. Response and error semantics

- `/api/v1` is the transport-version boundary. Responses do not repeat an ad hoc API `schemaVersion`; the source report version and `history-v1` projection version remain distinct.
- Existing report completeness (`complete|partial|failed`) and operation outcome (`completed|failed|cancelled`) remain independent. A missing report is `null`, not a zero-finding report.
- A successful empty history page differs from store/API failure. Unavailable, incompatible, corrupt, timed-out, unauthorized, invalid, or response-size-limited outcomes use the typed error envelope in [`requirements/ERROR-MODEL.md`](requirements/ERROR-MODEL.md). Parser-level request-target/header rejections are the explicit 414/431 exceptions described below.
- A valid detail record remains a `200` response when an associated raw artifact is missing, unreadable, or digest-mismatched. Each artifact reference carries an explicit integrity state; the API never serves artifact bytes or filesystem paths. This preserves trustworthy report metadata without claiming the evidence is available or verified.
- The API error envelope contains only a stable code and safe static message. It does not echo input, expose SQL/driver errors, or add a request ID without an approved use case.
- All API routes are bodyless; a prohibited body is `400 API_REQUEST_INVALID`, and there is no `API_REQUEST_TOO_LARGE` body error. Request targets above 2,048 bytes are rejected with transport-level 414; headers above 8,192 bytes with transport-level 431. These parser-boundary responses do not promise an API JSON error envelope. A disconnected client cancels work without a fabricated response; listener startup errors are CLI diagnostics, not HTTP responses.
- Existing v0.1/v0.2 scan error codes and CLI output/exit meanings remain unchanged.

## 6. Local security profile — owner decision pending

The following decisions are explicit proposals for the OpenAPI/security contract. None authorizes a listener implementation before owner acceptance and required technical evidence.

- Bind only `127.0.0.1:0`; let the OS allocate an ephemeral port. Never retry on wildcard, LAN, or public interfaces. The browser URL uses exactly `http://127.0.0.1:<selected-port>`; `localhost`, forwarded headers, and alternate host aliases are not trusted.
- Run the listener only within an explicit local-console command, not as a background service and never as a side effect of `deprail scan`. The command remains alive until shutdown, stops accepting requests on termination, drains bounded requests for at most 10 seconds, then closes storage. The command name is a separate CLI-contract decision.
- Require an opaque 256-bit process-scoped bearer token on every API route, including health. Generate it from a cryptographically secure random source; revoke it on process shutdown; keep it in browser memory only; never store it in local/session storage or cookies. Missing/invalid credentials return `401 API_AUTH_UNAUTHORIZED`.
Candidate bootstrap transfers the token only in an initial URL fragment; fragments are not sent in HTTP requests. The client must read it and immediately remove it with `history.replaceState` before making a request. The token is then sent only in the `Authorization` header. It must never appear in a path, query, referrer, log, diagnostic, or persisted browser storage. A reload or new tab loses the in-memory token; show a safe recovery state instructing the user to reopen the console from the active local CLI session, with no cookie/storage fallback. Fragment bootstrap remains a material owner security decision because it can be visible briefly in browser/OS launch state.
- For the selected fragment recommendation, remove the fragment before React rendering or any request; never print/log the credential URL. Use `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, a restrictive CSP, and local embedded assets only. The same-user/browser-launch exposure remains an explicit residual risk for owner security review, not a claim of protection against hostile same-user processes. See [ADR-0004's engineering selections](../../adr/ADR-0004-local-scan-history.md#detailed-engineering-selections-for-owner-review).
- Require the exact `Host` for the selected loopback port. If `Origin` is present, require an exact same-origin match; reject `null` and mismatched origins. If `Sec-Fetch-Site` is present, require `same-origin`. Do not emit CORS allow headers or trust forwarded headers. The bearer token remains required when `Origin` is absent.
- Accept `GET` only. Reject `HEAD`, `OPTIONS`, other methods, unknown query parameters, and all request bodies; return `405` for an unsupported method and `400 API_REQUEST_INVALID` for a prohibited body or invalid input. No filesystem path, SQL fragment, process operation, or artifact bytes are accepted from or returned to the client.
- Candidate finite bounds: request target 2,048 bytes (over-limit transport 414); headers 8,192 bytes (over-limit transport 431); eight concurrent requests; 10-second request deadline; 10-second shutdown drain; 1 MiB maximum response; page size 1–50 (default 25); cursor at most 512 characters. Saturation returns `503 API_BUSY`; a deadline returns `504 API_TIMEOUT`; an oversized response returns `500 API_RESPONSE_TOO_LARGE` without truncation. Parser-level 414/431 responses may not carry the API JSON envelope.
- Return `Cache-Control: no-store` for API responses. Never log authorization headers, tokens, sensitive request headers, raw paths, repository data, or database/stack details. Make no external network requests.
- If binding fails, report `API_LISTENER_UNAVAILABLE` safely and leave existing CLI commands usable.

The profile addresses DNS rebinding, hostile browser origins, local API authorization, request/resource bounds, and lifecycle behavior as one owner-reviewed proposal. Exact controls, token bootstrap, browser behavior, and residual risks require an explicit owner decision; independent review is optional.

## 7. Compatibility and versioning

The candidate source uses OpenAPI `3.1.0`, contract `info.version: 1.0.0`, and the `/api/v1` URL boundary. These versions are distinct from SQLite `user_version`, the `history-v1` projection, and a source `ScanReport` version. The OpenAPI file and examples must be validated before implementation; additive response evolution is not assumed safe for strict clients.

Breaking API changes require a new API version or an explicit reviewed migration. Existing CLI JSON, v1alpha report meaning, scan error codes, and exit-code behavior remain unchanged absent a separate compatibility decision. The embedded UI and API must ship as a matching version; mismatch fails visibly rather than serving empty or stale success.

## 11. Proposed console launch and static-service contract

The selected candidate command is `deprail web`, a foreground-only local console process. It starts no browser by default. `deprail web --open` asks the operating system to open the exact loopback console URL through the platform argv-based launcher (never a shell command). Interactive launcher failure is a safe stderr warning; noninteractive initial launch failure exits `3` as specified below. Unknown flags and extra positional arguments are CLI usage errors. This command and behavior are proposed, not accepted runtime behavior.

Console/query startup never creates or migrates missing history storage. It resolves the private root and queries existing supported storage read-only; absent storage is empty, unsupported/corrupt storage is a typed failure. Initialization and approved future migration belong only to explicit CLI capture.
On successful startup, print one concise line containing only the console origin/path (`http://127.0.0.1:<port>/console/`), never the token, fragment, or a credential-bearing URL. Opening the bare URL alone shows authentication-recovery guidance, not history. `deprail web --open` passes the exact URL with `#token=<token>` to the OS launcher using argv (never a shell); browser/OS launch state can briefly expose the fragment, an explicit residual risk for owner disposition. Without `--open`, no browser launches automatically. In an interactive stdin TTY, pressing Enter in the active foreground terminal invokes the argv launcher again with the same active process's exact fragment URL without printing or redisplaying the token. Non-TTY stdin requires `--open`; otherwise reject with usage exit `2` before startup, rather than leave a service without a usable credential-transfer path. Non-TTY reload recovery requires restarting the command with `--open`, preserving the database but revoking the old process token. The fragment is removed by first-party bootstrap synchronously before rendering or any fetch, then token remains only in browser memory and is sent only in `Authorization: Bearer …`. Never use cookies, storage, another auth endpoint, or token-in-query/path transmission.

`deprail web` usage errors (unknown flags, extra arguments, or non-TTY stdin without `--open`) exit `2` before listener startup. Listener bind/start failure emits a safe `API_LISTENER_UNAVAILABLE` diagnostic on stderr and exits `3`; it does not fall back to another interface. Interactive launcher failure leaves the listener running with a safe warning; noninteractive initial launcher failure stops it and exits `3`. Normal termination after signal exits `0`; an unexpected serve failure reports a safe `API_LISTENER_UNAVAILABLE` diagnostic and exits `3`. These exits belong only to `deprail web`, not scan behavior.

The process remains foreground until termination. On signal it stops accepting requests, cancels in-flight work, drains for at most 10 seconds, closes history storage and revokes its token. If reload/new tab loses the in-memory token, the static recovery state instructs the user to return to the active TTY terminal and press Enter, or restart `deprail web --open` for a noninteractive invocation; no credential URL is printed or redisplayed. Once the process ends, the credential is revoked. If the initial launcher fails and stdin is not a TTY, stop the unusable listener and exit `3` with a safe launch diagnostic; interactive launch failures remain warnings and permit an Enter retry.

Static console route set is exactly `/console/`, `/console/history`, `/console/scans/{historyEntryID}` (canonical UUIDv4), and `/console/about`, plus the declared hashed embedded assets. These are UI navigation routes, not API endpoints, do not require bearer auth, and may return the embedded console shell only for those exact UI paths. Unknown static routes return bounded non-reflecting 404; no SPA catch-all.
Serve only an explicit allowlist of embedded console asset paths and five API routes. No filesystem fallback, directory listing, arbitrary path, repository content serving, or executable repository strings are permitted. Declared hashed assets use exact embedded MIME types. Entry CSP is exactly `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; object-src 'none'`, with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; API responses are no-store. No external network assets.
An optional `--artifact-root <path>` selects an existing trusted artifact-store directory for resolving validated digest references; it does not scan repositories or accept a path through HTTP. Canonicalize and validate the directory at startup, then resolve only validated digest-addressed files beneath it, refusing symlink/reparse escapes. A supplied but inaccessible/invalid root is a safe startup error; when omitted, references are `unavailable`. Never persist or infer the root from a label, expose it in API/UI/errors/logs, or return artifact bytes. This is read-only integrity resolution, not export.
An invalid/inaccessible supplied artifact root is exit `2` (`CONFIG_INVALID`) before startup; a later artifact read failure is a per-reference `unavailable` state. Static entry documents and known assets accept only GET (HEAD/other methods receive 405 with `Allow: GET`); Origin, when present, must match the selected origin even on static routes. Cross-site static navigation may receive the non-secret shell, never the process credential or history.

Host must exactly match `127.0.0.1:<selected-port>`; reject alternate aliases and forwarded headers. For API requests, enforce exact same-origin when Origin is present and require `Sec-Fetch-Site: same-origin` when present. Do not apply API Fetch Metadata rejection to the top-level console navigation or same-origin static subresource loads: a browser's initial navigation can legitimately carry `Sec-Fetch-Site: none`. Reject `Origin: null` and mismatches. No CORS headers are emitted. Authentication is required even when Origin is absent.

## 12. Request mechanics and security precedence

Cursor encoding is canonical unpadded base64url (ASCII, maximum 512 bytes) over: one format-version byte (`0x01`), one resource byte (`0x01` history, `0x02` workspaces, `0x03` findings), a 16-byte parent UUID for child resources (omitted for history), then the last ordering tuple. Integers are network byte order. History tuple is signed int64 UTC Unix microseconds followed by the 16-byte history-entry UUID; finding tuple is the 32 raw bytes of lowercase-hex stableFindingKey. Workspace tuple is uint32 ordinal followed by SHA-256(workspaceID UTF-8 bytes), where ordinal is zero-based in the immutable, validated, workspaceID-ascending projection for that parent. On continuation, resolve ordinal in that same stored projection and require the hash to match before taking records strictly after the resolved actual workspaceID; malformed/out-of-range ordinal or mismatch is `API_REQUEST_INVALID`. This avoids putting a workspace/repository string in the cursor and does not add a source-ID length restriction. UUIDs use canonical textual UUID byte order. Exact decoded lengths are 26 bytes (history), 54 (workspace), and 50 (findings). Cursor binds `/api/v1`, resource and exact parent; it is non-authenticating, contains no credential or repository data, and requires no MAC because fields are validated against immutable stored data. Unsupported version/resource, malformed/noncanonical base64url, wrong parent, tuple, or byte length returns 400 `API_REQUEST_INVALID`.

Each page reads records strictly after its cursor in the documented total order. Scan candidates in that order and serialize each candidate with the complete response envelope and reserved `nextCursor`; emit only the longest prefix whose item count is within pageSize and whose actual UTF-8 JSON size is at most 1,048,576 bytes. If another record remains, cursor is based on the last emitted tuple. Do not advance over a record that did not fit. An empty first page is terminal only when no record exists; a nonterminal page must contain at least one item. If the first eligible record cannot fit with the required envelope/cursor, return `500 API_RESPONSE_TOO_LARGE` before writing a success body. Detail responses are indivisible and follow the same cap. No snapshot isolation is promised; inserts before the cursor may be omitted until the client restarts pagination.

Admission order: transport parser enforces request-target (2,048 bytes) and aggregate header (8,192 bytes) limits, producing transport 414/431 without guaranteed API envelope. Then exact Host validation; framing/body rejection (400); method (known route non-GET gets 405); route/version resolution (unknown path/version 404); query/identifier validation (400); Origin and API Fetch Metadata policy (403); bearer authentication (401); then acquire one of at most eight in-flight slots or return 503 `API_BUSY`. Unknown route/version and unsupported method use `API_ROUTE_NOT_FOUND`, `API_VERSION_UNSUPPORTED`, and `API_METHOD_UNSUPPORTED`; no unbounded queue. Authentication precedes storage access; invalid input does not access storage. Ten-second deadline covers admission through response serialization/write; expiry maps to 504 `API_TIMEOUT` if response remains possible. Client disconnect cancels storage work and sends no fabricated response. Projection/store errors retain their error-model classes: `HISTORY_CORRUPT` is 500; `HISTORY_UNAVAILABLE`, `HISTORY_SCHEMA_UNSUPPORTED`, and `HISTORY_MIGRATION_FAILED` are 503. They never become empty success.

## 13. Exact route and error boundary

The static console document/assets are not API endpoints and do not require the API bearer token; they are served only on the exact loopback Host, have no filesystem fallback, and contain no secret. The optional trusted artifact-store root is provided only by CLI and never returned or accepted by API. All five API routes, including health, require bearer auth. The sole API operations are `GET /api/v1/health`, `GET /api/v1/scans`, `GET /api/v1/scans/{historyEntryID}`, and GET on each `/workspaces` and `/findings` child collection. HEAD, OPTIONS, every other method/path, and every mutation/auth/bootstrap route are unsupported.

Route errors use OpenAPI's existing safe status/code sets: 400 `API_REQUEST_INVALID`; 401 `API_AUTH_UNAUTHORIZED`; 403 `API_ORIGIN_REJECTED`; 404 `HISTORY_ENTRY_NOT_FOUND`, `API_ROUTE_NOT_FOUND`, or `API_VERSION_UNSUPPORTED`; 405 `API_METHOD_UNSUPPORTED`; 500 `API_INTERNAL_ERROR`, `API_RESPONSE_TOO_LARGE`, or `HISTORY_CORRUPT`; 503 `API_BUSY`, `HISTORY_UNAVAILABLE`, `HISTORY_SCHEMA_UNSUPPORTED`, or `HISTORY_MIGRATION_FAILED`; 504 `API_TIMEOUT`. Parser 414/431 are transport exceptions, not API errors. Errors use static safe messages and never expose SQL, driver details, paths, stacks, raw roots/errors, unknown projection fields, or echoed inputs. Do not return 200 with fabricated empty data on storage, projection, corruption or incompatibility failure.

These details reconcile the candidate engineering selection in ADR-0004 §Detailed engineering selections. Earlier sections and historical drafts that call particular controls “unresolved” describe the state before this selection; owner acceptance and runtime evidence remain pending.
